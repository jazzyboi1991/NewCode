# NewCodeSpeak 전체 개발 계획

## 1. 목표와 범위

NewCodeSpeak는 조지 오웰의 *1984*에 등장하는 신어의 통제 방식을 비판적으로 탐구하는 작은 프로그래밍 언어다. 첫 번째 릴리스의 목표는 명세서에 적힌 문법과 검열 규칙을 실제로 실행할 수 있는 명령줄 인터프리터를 만드는 것이다.

첫 릴리스에서는 다음을 제공한다.

- `.ncs` 소스 파일의 어휘 검열, 구문 분석, 실행
- `approve`, `set`, `fact`, `rule`, `query`, `proclaim`, `if`, `repeat while` 지원
- 최신 `fact`가 이전 기록을 덮어쓰는 현재-기록 모델
- 승인되지 않은 식별자·문자열·주석에 대한 위치가 포함된 오류 메시지
- 예제와 자동 테스트

웹 IDE, GUI, 최적화 컴파일러, 파일 입출력, 함수·배열·사용자 정의 자료형은 첫 릴리스의 범위에서 제외한다. 언어의 작은 표현력 자체가 작품의 주제이므로, 기능 확장은 반드시 명세의 비판적 의도와 함께 검토한다.

## 2. 구현 원칙

- 구현 언어는 Python으로 한다. 빠르게 읽을 수 있는 참조 인터프리터와 테스트 도구를 만들기에 적합하다.
- 영어 키워드만 실제 소스 코드로 허용한다. 한국어는 문서와 진단 메시지에 사용한다.
- 검열은 파싱보다 먼저 수행한다. 주석과 문자열도 예외가 아니다.
- 오류를 조용히 무시하지 않는다. 어떤 단어가 어느 줄·열에서 승인되지 않았는지 표시한다.
- 사실의 과거 이력은 실행 상태에 보존하지 않는다. 같은 사실 주소에는 가장 최근 값만 남긴다.
- 구현의 동작이 문서와 다르면 구현을 임의로 넓히지 않고, 먼저 명세를 수정한다.

## 4. 단계별 개발 계획

### 단계 0 — 명세 동결과 결정 기록

README의 EBNF와 의미 규칙을 구현 가능한 체크리스트로 옮긴다. 특히 다음 모호성을 먼저 확정한다.

- `proposition`의 첫 이름은 주어, 뒤의 선택 이름들은 속성으로 해석한다. 예: `citizen obey party`의 주소는 `citizen / obey party`다.
- `fact citizen is good`의 주소는 `citizen / is`, 상태는 `good`이다.
- `query`의 결과는 표준 출력에 한 줄로 출력한다.
- `rule A when B`는 질의 직전과 제어 조건 평가 직전에 고정점에 도달할 때까지 적용한다. 더 이상 새 사실이 생기지 않으면 멈춘다.
- 규칙 순환 또는 무한 반복은 실행 제한으로 보호한다. 초기값은 규칙 적용 1,000회, 반복 10,000회로 둔다.

완료 기준: 위 결정이 README 또는 별도 `DECISIONS.md`에 기록되고, 각 항목에 대응하는 테스트 이름이 정해져 있다.

### 단계 1 — 프로젝트 골격과 실행 명령

Python 패키지와 테스트 환경을 만든다. `ncs examples/conforming.ncs`처럼 실행할 수 있는 CLI 진입점을 제공한다. 아직은 파일을 읽어 내용만 표시하거나 “not implemented” 오류를 내도 된다.

완료 기준:

- 가상 환경에서 의존성 설치와 테스트 실행이 가능하다.
- 존재하지 않는 파일, 잘못된 인코딩, 빈 파일에 대해 이해 가능한 오류가 나온다.
- `--help`, `--version`이 동작한다.

### 단계 2 — 어휘 정책과 검열기

`vocabulary.py`에 명세의 기본 승인 어휘와 이름 규칙(`[a-z_]+`)을 정의한다. `censor.py`는 소스 전체를 스캔해 첫 `approve` 문장에서 승인된 사용자 이름을 모으고, 그 밖의 단어를 거부한다.

검열기는 코드, 큰따옴표 문자열, 한 줄 주석(`//`)을 모두 검사한다. 숫자와 문장부호는 단어로 취급하지 않는다. 오류에는 파일명·줄·열·문제 단어·간단한 이유를 포함한다.

완료 기준:

- 승인되지 않은 변수, 문자열 속 단어, 주석 속 단어가 각각 거부된다.
- 승인 목록 이전에 사용자 정의 이름을 쓰면 거부된다.
- 기본 키워드는 별도 승인 없이 통과한다.
- 잘못된 이름(대문자, 숫자 포함, 하이픈 포함)이 거부된다.

### 단계 3 — 렉서와 AST

검열을 통과한 소스를 토큰으로 분해한다. 줄·열 위치를 모든 토큰에 보존한다. 이어서 명세의 각 문장을 표현할 불변 AST 자료형을 작성한다.

필요한 토큰은 이름, 정수, 세미콜론, 쉼표, 키워드, 줄바꿈 또는 EOF다. 들여쓰기는 문법 요소가 아니며 `end`가 블록의 끝을 결정한다.

완료 기준:

- 정상 예제의 토큰열과 AST가 기대값과 일치한다.
- 닫히지 않은 블록, 누락된 세미콜론, 잘못된 `approve` 목록을 구문 오류로 보고한다.
- 오류 위치가 실제 문제 지점을 가리킨다.

### 단계 4 — 파서 구현

재귀 하향 파서로 EBNF를 구현한다. 산술식은 `plus`와 `minus`, 조건식은 `above`, `below`, `and`, `or`를 지원한다. 연산자 우선순위는 다음처럼 고정한다.

```text
값/비교  →  plus·minus  →  and  →  or
```

`if ... then ... else ... end`와 `repeat while ... end`의 문장 목록을 올바르게 중첩 처리한다.

완료 기준:

- README의 실행 가능한 예제가 파싱된다.
- 중첩 `if`와 `repeat`가 정확히 AST로 표현된다.
- 모호하거나 명세에 없는 문법은 허용하지 않는다.

### 단계 5 — 실행 상태와 기본 평가기

`runtime.py`에 다음 상태를 구현한다.

- 변수 저장소: `set`으로 설정된 이름과 정수 또는 승인 상태 값
- 현재 사실 기록: `(주어, 속성) → 상태` 매핑
- 규칙 목록: 조건 명제와 결과 명제
- 출력 버퍼 또는 표준 출력

`set`, 산술식, 비교식, `and`/`or`, `if`, `repeat while`, `proclaim`을 먼저 구현한다. 정의되지 않은 변수, 숫자가 아닌 산술, 제한 초과 반복은 실행 오류로 처리한다.

완료 기준:

- 할당, 산술, 조건, 반복의 정상·오류 사례가 자동 테스트를 통과한다.
- `proclaim`은 승인 어휘로만 구성된 출력만 만든다.
- 반복 제한을 초과하는 프로그램이 안전하게 중단된다.

### 단계 6 — 사실 교체와 규칙 엔진

`fact`는 현재 사실 기록만 갱신한다. 같은 `(주어, 속성)` 주소의 기존 값은 새 상태로 완전히 교체한다. 이때 오래된 값을 별도 로그에 남기지 않는다.

`rule A when B`는 현재 기록에서 B가 참일 때 A를 참으로 만든다. 규칙 적용은 고정점까지 반복하되, 변경이 없으면 멈춘다. `query`는 규칙을 적용한 뒤 현재 상태를 출력한다.

완료 기준:

- 같은 주소에 두 `fact`를 기록하면 최신 상태만 질의된다.
- 규칙 연쇄(A ← B ← C)가 한 번의 질의에서 모두 반영된다.
- 거짓 또는 없는 전제는 규칙 결과를 만들지 않는다.
- 규칙 적용 제한을 넘는 순환은 오류로 중단된다.

### 단계 7 — CLI 진단과 사용자 경험

실행 흐름을 `읽기 → 검열 → 렉싱 → 파싱 → 실행`으로 연결한다. 각 단계의 오류를 같은 형식으로 표시하고, 종료 코드를 구분한다.

```text
파일:줄:열: 오류 종류: 설명
  문제의 원본 줄
  ^
```

권장 종료 코드: 0(성공), 2(검열 오류), 3(구문 오류), 4(실행 오류), 5(입출력 오류)로 한다. `--dump-tokens`, `--dump-ast`는 개발용 선택 기능으로 제공할 수 있다.

완료 기준:

- 검열·구문·실행 오류가 서로 구별되어 표시된다.
- README의 검열 예제 세 개가 각각 검열 오류로 실패한다.
- 정상 프로그램의 출력과 종료 코드가 예측 가능하다.

### 단계 8 — 문서, 예제, 테스트 강화

README의 문법·의미·예제를 구현과 대조하고, 실제로 실행되는 `.ncs` 예제를 추가한다. 각 명세 규칙에는 최소 하나의 정상 테스트와 하나의 거부 또는 경계 테스트를 둔다.

테스트는 다음 범주를 포함한다.

- 승인 목록과 이름 규칙
- 코드·문자열·주석 검열
- 모든 문장 종류와 중첩 블록
- 표현식 우선순위와 자료형 오류
- 사실 덮어쓰기와 규칙 연쇄
- 반복·규칙 제한
- CLI 출력과 종료 코드

완료 기준:

- README의 모든 코드 블록이 실행 가능 또는 의도적으로 거부되는 사례로 분류되어 있다.
- 테스트가 한 명령으로 실행되고 모두 통과한다.
- 새 기여자가 README만 보고 설치·실행·실패 원인을 이해할 수 있다.

### 단계 9 — 첫 릴리스 검수

빈 새 환경에서 설치부터 예제 실행까지 재현한다. 명세와 실제 동작의 차이를 확인하고, 발견된 차이는 구현 버그 또는 문서 버그로 명확히 분류한다. 릴리스 태그와 변경 기록을 만든다.

완료 기준:

- 전체 테스트 통과
- 정상 예제 2개 이상과 검열 예제 3개 이상이 CLI에서 재현됨
- 알려진 제한 사항이 README에 적힘
- 버전 번호가 부여된 첫 릴리스가 준비됨

## 6. 첫 구현 뒤의 확장 후보

확장은 언어를 편리하게 만드는 방향보다, 통제가 표현과 계산을 어떻게 바꾸는지 드러내는 방향을 우선한다.

- 실행 추적 모드: 현재 상태만 보이게 하는 기본 모드와 달리, 교육 목적으로 사실이 교체되는 순간만 시각화한다. 기본 언어 의미에는 과거를 되돌리지 않는다.
- 승인 정책 파일: 당의 기본 어휘를 외부 정책 파일로 바꾸어, 어휘 변화가 프로그램 가능성에 미치는 영향을 실험한다.
- 브라우저 데모: 검열 오류와 현재 기록의 변화를 교육용 화면으로 보여 준다.
- 한국어 오류 메시지와 영어 오류 메시지 전환 옵션
- 금지 어휘 목록의 단순 치환이 아니라 주제별 정책을 시험하는 실험 모드

함수, 일반 문자열, 파일 입출력처럼 표현력을 크게 늘리는 기능은 언어의 핵심 실험을 약화시킬 수 있으므로, 별도 설계 문서와 반례 테스트 없이는 추가하지 않는다.

## 7. 위험 요소와 대응

| 위험 | 대응 |
| --- | --- |
| 명세의 명제 구조가 모호함 | 단계 0에서 주소·상태·규칙의 의미를 예제와 함께 고정한다. |
| 검열기가 파서와 다르게 단어를 분리함 | 단어 경계 규칙을 한 모듈에 두고 검열기와 렉서가 공유한다. |
| 규칙 순환 또는 반복문이 멈추지 않음 | 적용·반복 횟수 제한과 명확한 실행 오류를 둔다. |
| 검열이 단순 금칙어 필터처럼 보임 | 문자열과 주석까지 검사하고, 문서에서 이것이 비판적 실험임을 반복해 명시한다. |
| 문서와 구현이 어긋남 | README 예제를 통합 테스트로 실행한다. |

## 8. 완료 정의

다음 조건을 모두 만족하면 첫 릴리스를 완료로 본다.

1. README의 정식 문법에 있는 모든 구문이 구현되어 있다.
2. 승인되지 않은 단어는 코드·문자열·주석 어디에서도 실행 전에 통과하지 못한다.
3. 가장 최근 `fact`만 현재 기록에 남고, `rule`과 `query`가 그 기록만 사용한다.
4. 정상·검열·구문·실행 오류 사례가 자동 테스트로 보호된다.
5. 새 사용자가 CLI로 예제를 실행하고 오류를 이해할 수 있다.
